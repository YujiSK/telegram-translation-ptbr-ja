# Project Rules

This is the canonical source for coding and process rules in this repository.
`CLAUDE.md`, `AGENTS.md`, and the Claude Skill all point here instead of
duplicating these rules — if you're updating a rule, update it here.

## Source layout (target state)

The codebase will grow into this structure. Not all of these directories
exist yet (see `docs/implementation-plan.md` for when each is introduced).

```text
src/
├── index.ts
├── config/
├── domain/
├── application/
├── infrastructure/
│   ├── d1/
│   ├── openai/
│   └── telegram/
├── handlers/
├── commands/
├── prompts/
└── shared/
```

### Responsibilities

- **`domain/`** — Types and rules with no dependency on external services.
  Pure TypeScript: no `fetch`, no bindings, no SDKs.
- **`application/`** — Use cases (translation flow, speaker-memory
  read/write flow). Orchestrates `domain/` and `infrastructure/`, but
  contains no HTTP or SDK-specific code itself.
- **`infrastructure/d1/`** — All D1 access. Owns SQL and D1 result parsing.
- **`infrastructure/openai/`** — All OpenAI API access.
- **`infrastructure/telegram/`** — All Telegram Bot API access.
- **`handlers/`** — HTTP/webhook entry points. Thin: parse the request,
  call into `application/`, format the response.
- **`commands/`** — Telegram slash-command implementations
  (`/status`, `/profile`, etc.).
- **`prompts/`** — Versioned OpenAI prompt templates.
- **`shared/`** — Small, generic helpers with no domain knowledge.
- **`config/`** — Reads and validates non-secret configuration (secrets
  come from bindings/env directly, not through this layer).

## Hard rules

These apply to every phase, not just Phase 0.

1. **No external-service dependencies in `domain/`.** Domain types and
   rules must compile and be testable with no Telegram, OpenAI, or D1
   imports.
2. **Never treat a raw Telegram, OpenAI, or D1 response as a domain type.**
   Convert at the infrastructure boundary; `domain/` only sees converted,
   validated shapes.
3. **All SQL is parameterized.** No string-built SQL with interpolated
   values, ever — including for admin/internal tooling.
4. **No request-scoped data in module-level mutable variables.** Workers
   reuse isolates across requests; module-level mutable state leaks
   between unrelated requests/users.
5. **No unhandled/floating Promises.** Every Promise is `await`ed,
   returned, or explicitly passed to `ctx.waitUntil()`. Enforced by
   `@typescript-eslint/no-floating-promises` in `eslint.config.js`.
6. **All external API calls (Telegram, OpenAI) have a timeout.** Use
   `AbortSignal.timeout(...)` or equivalent — never an unbounded `fetch`.
7. **Retries are limited to transient errors** (network failures, 429,
   5xx). Never retry on 4xx client errors other than 429, and never retry
   on validation/parsing failures.
8. **Retry counts are capped.** No unbounded or open-ended retry loops.
9. **Never log message text or Secrets.** Structured logs may include IDs,
   status, timing, and error codes/classes — never raw Telegram message
   content, prompts sent to OpenAI, or Secret values. See
   `docs/security-and-privacy.md`.
10. **Never write Secrets into source, README, or committed config files.**
    Secrets are registered via `wrangler secret put` (production) or
    `.dev.vars` (local, gitignored). See `docs/security-and-privacy.md`.
11. **No `any` and no unsafe double-casts** (`as unknown as X`). Enforced
    by `@typescript-eslint/no-explicit-any` in `eslint.config.js`. If a
    type is genuinely unknown at a boundary, narrow it with a type guard
    or a validation function instead.
12. **Use Cloudflare Bindings, not the REST API,** for D1, and any future
    Cloudflare product (KV, R2, etc.). Bindings are in-process and
    unauthenticated-by-default; the REST API is for tooling outside the
    Worker, not for the Worker's own runtime code.
13. **One implementation-plan phase per change.** Do not implement Phase
    N+1 work while Phase N is in progress. See
    `docs/implementation-plan.md`.
14. **Verify before moving on.** At the end of a phase, run
    `npm run check` (format, lint, typecheck, test) and confirm it's
    green before starting the next phase.

## Binding names (reserved, not yet configured)

These names are reserved for when the corresponding bindings are actually
added (see `docs/implementation-plan.md`, Phase 2+). Do not add the
binding to `wrangler.jsonc` before its phase.

| Binding | Purpose                                       |
| ------- | --------------------------------------------- |
| `DB`    | D1 database (speaker memory, allowlist, etc.) |

## Generated files

- `worker-configuration.d.ts` is generated by `npm run cf-typegen`
  (`wrangler types`). It is committed so CI and fresh clones don't need
  Cloudflare account access just to typecheck. Regenerate and commit it
  whenever `wrangler.jsonc` bindings change — never hand-edit it.

## Compatibility flags

`nodejs_compat` is intentionally **not** set yet. Add it only in the phase
that first needs a Node.js built-in (for example, if the OpenAI or
Telegram HTTP client ends up requiring one), and note why in this file
when it happens. Don't add compatibility flags speculatively.
